## Tools, Autonomy & Safety

本文件定义 openpup 的工具分层、自主性机制，以及特别针对「帮我炒股、能执行动作」场景的安全模型。

---

### 1. 工具分层模型

所有可以「影响外部世界」的能力，都必须抽象为工具（Tool），并按照风险分层：

#### L1 – Read Only（只读）

- **能力**
  - 读取数据：行情、新闻、财报、邮件头、日历、任务、Home Assistant 状态等
  - 不修改外部系统任何状态
- **用例**
  - 投资：扫描市场、生成早盘简报、生成收盘复盘
  - 工作：整理今日会议与待办、邮件/消息归类
  - 生活：查看家居当前状态、天气、日程
- **约束**
  - 可以默认启用，无需手动审批
  - 对敏感数据的读取仍需最小化（例如不读取完整邮件正文，只读摘要）

#### L2 – Draft（草稿）

- **能力**
  - 生成对外输出或操作的「草稿」版本：
    - 邮件内容、文案、报告、周报
    - 交易计划（标的、方向、数量、价格区间、理由、风险说明）
    - Home Assistant 自动化方案（拟执行动作列表）
- **用例**
  - 助手作为「顾问」，给你候选方案与结构化计划
  - 由你来决定是否采纳与执行
- **约束**
  - 不直接调用任何会改变外部状态的 API/浏览器操作
  - 所有草稿要写入本地日志，便于审计和复盘

#### L3 – Auto Safe（低风险自动执行）

- **能力**
  - 自动执行一组被认为是「低风险、可容错」的动作：
    - 家居：关灯、关空调、拉窗帘、切换到预设场景
    - 文档：生成日报/周报文件并存到本地指定目录
    - 投资：仅限模拟盘 / 小额定投之类的严格受限操作
- **用例**
  - 早晚例行动作、离家/回家场景
  - 自动整理日志和报表
- **约束**
  - 必须在 Persona/Playbook 中写明：
    - 允许自动执行的场景
    - 允许的时间窗口（例如深夜不做大动作）
    - 白名单（允许操作的设备/文件/标的）
  - 所有执行必须有结构化日志记录

#### L4 – High-Risk（高风险执行）

- **能力**
  - 直接改变高价值资产或系统配置的动作：
    - 真实资金交易（特别是大额或高频）
    - 安防系统配置修改
    - 带来严重后果的系统命令
- **用例**
  - 默认不使用。即使使用，只在极少数场景以「需要强确认」方式存在。
- **约束**
  - 默认关闭，配置文件中不启用对应工具
  - 如果未来启用，必须满足：
    - 多重确认（例如在飞书/Telegram 中用指定命令格式确认）
    - 严格额度/频次上限
    - 独立的审计与报警机制

### 2. 自主性设计：从被动到主动（Loop = Playbook，而不是硬编码）

自主性不是「放飞」，而是在规则内进行自动行动。核心由三部分组成：

#### 2.1 事件源（Triggers）

- **时间型**
  - Cron / Heartbeat 任务：
    - 每日早晨：工作计划 + 投资扫盘
    - 每日晚间：工作复盘 + 投资复盘 + 家居睡前场景
    - 每周/每月：周报/月报与资产复盘

- **事件型**
  - 消息事件：飞书/Telegram 的新消息、指令、@提及
  - 家居事件：Home Assistant 的在家/离家、传感器状态变化
  - 市场事件：行情/监控信号（例如价格突破区间、成交量异常）

#### 2.2 目标与任务（Goals & Tasks）

- **目标（Goals）**
  - 例如：
    - 保持工作任务有序推进（不积压、不遗忘）
    - 保持投资组合风险在合理区间
    - 保持家庭环境舒适安全
- **任务（Tasks）**
  - 由目标拆解而来，具有：
    - 上下文（来源事件、相关记忆）
    - 优先级（高/中/低）
    - 所需工具与权限级别

助手的「主动性」就是：在事件到来时，根据 Persona 与 Memory，决定要创建/更新哪些任务，并在安全边界内执行。
这些决策应当由 **Playbook/配置** 驱动，而不是直接写死在 Rust 代码中：
- Playbook 定义「遇到什么事件，按什么流程、以什么工具执行」；
- 代码仅负责解释 Playbook、调度工具、写审计。

#### 2.3 行为循环（Action Loop）

1. **感知（Perceive）**：从事件源获取信息，必要时访问记忆
2. **理解（Understand）**：结合 Persona 判断重要性与紧急程度
3. **决策（Decide）**：决定：
   - 是否创建/更新任务
   - 使用哪些工具、需要什么权限级别
4. **行动（Act）**：执行只读/草稿/自动执行动作
5. **记录（Log）**：将关键动作与决策摘要写入日志与记忆
6. **反馈（Inform）**：在适当的渠道（飞书/Telegram）通知用户

换句话说：**Loop 是「人」的习惯与流程的外化，不是工程师硬编码的一段脚本**。代码实现 Loop，只能实现这个六步骨架和安全边界，具体「做什么工作」「如何拆解任务」应该来自 Playbook 与 Persona。

---

### 2.4 人 → 爪子 → 工具

- **人**：Persona + 记忆 + 价值观 + Playbook，决定「为什么」「该不该」。
- **爪子**：行为循环与调度逻辑（本节的 Action Loop + scheduler），决定「什么时候」「如何编排多个工具与任务」。
- **工具**：底层的 HTTP/浏览器/家居/交易等原子能力，只负责「怎么执行」。

设计与实现上的硬约束：
- 新增高层行为时，优先修改 Persona/Playbook/配置，而不是直接在 Loop 代码中硬编码业务逻辑。
- Loop 代码的职责是：读取配置/Playbook → 触发/编排工具 → 写审计 → 更新记忆；不得在代码中塞入具体业务条款（如某只股票的买卖规则、某个家庭场景的具体设备列表），这些应留给 Playbook。

### 3. 券商网页交易场景的特别设计

由于不使用 API，而是通过浏览器模拟操作进行交易，本场景需要更强的安全约束。

#### 3.1 浏览器 Sidecar 工具

- **功能**
  - 通过 DevTools 协议或自动化框架（如 Playwright/Selenium 等）控制浏览器：
    - 打开券商网页、登录、导航至交易页面
    - 填写买卖订单表单
    - 读取确认页面的关键信息（标的、价格、数量、方向）
    - 截图/记录页面状态

- **安全约束**
  - **域名白名单**：只允许访问东方财富及指定券商网页域名
  - **操作模板**：使用固定的 DOM/选择器模板，而不是任意点击
  - **会话隔离**：尽量在专用浏览器实例或专用用户配置目录下运行

#### 3.2 交易工具的分层使用

- **L1/L2：分析与计划阶段**
  - 工具：`invest_scan_market`, `invest_generate_plan`
  - 输出：
    - 推荐关注标的列表
    - 每个标的对应的交易计划草稿（包括风险说明）
  - 不调用浏览器 Sidecar 的下单能力

- **L3：模拟盘自动执行**
  - 工具：`invest_paper_trade_execute`
  - 行为：
    - 在模拟盘或专门的「训练环境」中，按照交易计划执行下单
    - 记录下单参数与页面截图
  - 约束：
    - 请确保使用券商/第三方平台提供的模拟登录或专用账户
    - 金额、频次和持仓规模仍需有限制（为了习惯与策略迁移时安全）

- **L4：实盘执行（暂不默认启用）**
  - 工具：`invest_live_trade_execute`
  - 仅在未来明确要求时考虑开启，并加上：
    - 人工确认命令（如在飞书/Telegram 输入“确认执行计划 #PLAN_ID”）
    - 金额/频次/总敞口的硬限制
    - 异常报警机制（如交易失败、网络错误、DOM 结构变化）

### 4. 安全与信任总则

#### 4.1 权限分级与边界

- 每个工具必须声明：
  - 自己的权限级别（L1–L4）
  - 可访问的资源范围（域名/设备/文件路径）
  - 是否可以在「无人值守」状态下被调用

- 系统全局默认策略：
  - 仅 L1 与部分 L2 工具可在无明确授权的情况下使用
  - L3 工具需在 Persona/Playbook 中对场景做白名单配置
  - L4 工具默认禁用

#### 4.2 审计与可解释性

- 所有 L3/L4 工具调用，以及任何「自主行为」（定时 Loop / 事件驱动行为 / Spawn 尝试），必须产生结构化审计记录。

- 审计事件建议包含：
  - 时间戳
  - Realm（公司/部门/王朝）与 Agent（core / 某个 worker）
  - 触发源（时间 / 消息 / 行情 / 家居事件等）
  - 决策摘要（目标、计划概要、预期使用的工具）
  - 实际工具调用列表（名称、等级 L1–L4，参数的脱敏摘要）
  - 执行结果（成功/失败/跳过）与异常信息（如有）
  - 风险标记（是否触及金融 / Spawn / 其他高危路径）

- 每日/每周自动生成「动作审计摘要」，供造物主快速检查：
  - 自动执行了哪些事情（按 Realm / Agent / 风险等级聚合）
  - 是否有接近边界或被拒绝的动作

#### 4.3 紧急停止与降权

- 提供一键命令（例如在飞书/Telegram 中输入特定指令）：
  - 立即将系统切换到：
    - 只读模式（禁止一切修改外部状态）
    - 或草稿模式（允许生成建议与草稿，但不执行）

- 在出现以下情况时自动降级：
  - 检测到异常行为（频繁下单、非白名单域名、家居设备异常闪烁）
  - 外部系统（券商/家居/网络）返回错误或结构变化

### 5. 自我复制与扩张（Spawn / Replication）

openpup 支持在概念上「克隆自己」「扩张王朝」，但**所有自我复制能力必须是显式授权的高层行为**，而不是默认能力。

#### 5.1 自我复制的构成动作

典型的自复制流程通常包含若干高危子动作：

- 登录远程服务器（SSH / API）
- 安装 openpup / Rust / 依赖环境
- 拉取 openpup 代码库并构建
- 启动新的 openpup 实例
- 把新实例注册为当前系统的子节点（Worker / Realm 成员）

这些动作本身都可能改变外部世界（安装软件、打开端口、拉起服务），因此必须纳入严格的工具分层与权限管理。

#### 5.2 自复制权限级别

在工具分层（L1–L4）之上，对「自复制相关能力」再定义一组开关：

- **Spawn:disabled（默认）**
  - 禁止一切形式的自动自复制。
  - 允许助手提出「扩张计划草稿」（例如在哪些机器上部署什么），但不执行任何实际动作。

- **Spawn:proposal-only**
  - 允许助手：
    - 发现可用服务器/资源（只读）
    - 生成部署计划与命令脚本草稿
  - 所有执行仍需你在本地或远程手工运行（或通过显式命令触发）。

- **Spawn:supervised**
  - 允许在你明确批准后，由工具自动执行部分部署步骤：
    - 例如：执行经你确认后的脚本、安装依赖、拉取代码
  - 仍然禁止自动开放对外端口或创建具有高权限的账号。

- **Spawn:autonomous（不推荐，需显式启用）**
  - 允许在限定的环境/白名单内全自动完成自复制流程。
  - 必须受以下约束：
    - 白名单服务器/网络段
    - 严格的资源上限（实例数量、CPU/RAM、端口范围）
    - 单独的审计与报警机制

#### 5.3 配置建议

建议在 openpup 的高层配置中显式声明类似字段。实际路径：`~/.openpup/config.toml`。示意：

```toml
[autonomy.spawn]
mode = "disabled"          # "disabled" | "proposal-only" | "supervised" | "autonomous"
allowed_hosts = []         # 允许自复制的主机/IP/标签列表
max_workers = 0            # 最大允许的 Worker 数量（0 表示禁止新增）
require_manual_approval = true
```

自复制相关工具本身也应标注清楚：

- 使用到的 SSH/云 API 凭证范围
- 可以安装/修改的软件种类
- 是否允许在新节点上进一步进行自复制（防止无限递归）

---

本文件的目标，是让未来在实现具体工具与任务调度时，有一套清晰的「能力边界与防线设计」。在编写 openpup（或其他 Agent OS）的工具定义和配置文件时，应当显式标出每个工具对应的层级，并在代码与配置层面双重约束；涉及自复制与扩张的能力，应额外受 `autonomy.spawn` 策略约束，并默认关闭。

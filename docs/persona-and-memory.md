## Persona & Memory Design

本文件定义 openPup 的人格（Persona）与记忆（Memory）体系，目标是让助手在「决策风格、表达方式、风险偏好」上尽可能接近用户本人，并在此基础上安全地使用记忆。

---

### 1. Persona（人格）结构

Persona 不是一段 Prompt，而是一组可组合、可长期维护的文档。openPup 默认在 **`~/.openpup/workspace/persona/`** 下使用四个文件来表达人格：

- `IDENTITY.md` – 基本身份与长期目标  
- `SOUL.md` – 价值观与红线  
- `USER.md` – 当前用户状态与偏好  
- `TOOLS.md` – 工具使用哲学与权限分级  

#### 1.1 `IDENTITY.md` – 我是谁

用于回答「你是谁」「你为谁工作」「你的长期目标是什么」。

```markdown
# IDENTITY – 我是谁

- 职业/角色：
- 长期目标（事业 / 资产 / 生活）：
- 决策风格（偏数据 / 偏直觉 / 偏保守 / 偏进取）：
- 语言与沟通偏好：

# 关键设定

- 我只为谁服务：
- 我不做哪些类型的工作：
- 我默认关注的领域：
```

#### 1.2 `SOUL.md` – 价值观与红线

用于定义 openPup 在任何时候都不能越过的边界，尤其是金融、隐私、安全相关。

```markdown
# SOUL – 价值观与红线

## 价值观
- 先保命再赚钱，长期主义，不做自己不理解的事。
- 尊重隐私与安全，不轻易扩大攻击面。

## 金融红线
- 不使用杠杆，不卖空，无期权/衍生品操作。
- 单笔投入不超过流动资金 X%。
- 总权益资产敞口不超过净资产 Y%。

## 行为红线
- 不伪造身份，不绕过安全机制，不做违法行为。
- 不对家庭/隐私/资产造成不可逆损害。
```

#### 1.3 `USER.md` – 当前用户状态与偏好

用于描述当前你的生活/工作状态，时间偏好，沟通偏好等。

```markdown
# USER – 当前用户状态与偏好

- 当前生活/工作状态：
- 时间偏好（深度工作时段）：
- 沟通偏好（简洁/长文、结构化程度）：
- 风险承受能力（工作/投资/生活）：
```

#### 1.4 `TOOLS.md` – 工具使用哲学与权限分级

用于声明各类工具在不同场景下允许的等级（L1–L4），以及需要人工确认的规则。

```markdown
# TOOLS – 工具使用哲学与权限分级

- 能自动化解决的重复劳动尽量自动化；高风险/不可逆操作必须经过明确说明与确认。
- 当前阶段：仅允许 L1（只读）与 L2（草稿），不执行 L3/L4 自动动作。
```

在 openPup runtime 中，应当按场景（工作 / 投资 / 生活）**选择性地注入**这些文档片段，而不是一次性全部塞入上下文。

---

### 2. 三层记忆体系

记忆不是「一个大向量库」，而是分层与分用途的系统。

#### 2.1 短期会话记忆（Session Memory）

- **用途**
  - 追踪当前对话的上下文、当前任务的状态
  - 支持多轮对话、任务拆分和修正
- **实现建议**
  - 使用 openPup runtime 的会话上下文 + 简单压缩/总结策略
  - 对每个会话维护：
    - 最近 N 条消息
    - 一个「小结」字段，定期更新以防上下文爆炸
- **注意点**
  - 不在会话记忆中存储敏感凭证（账号/密码/验证码）
  - 对含隐私的内容进行最小必要记录（记录意图而非原文）

#### 2.2 长期语义记忆（Semantic Memory）

- **用途**
  - 记住用户的长期偏好、反复出现的模式与关键知识点
  - 用于跨任务的「了解你是谁」与「你是怎么决策的」
- **实现建议**
  - 使用本地 SQLite + FTS + 向量检索（openPup 默认支持的记忆后端之一）
  - 建立定期写入机制：
    - 每日/每周生成 `WORK_LOG.md` 和 `INVEST_LOG.md`
    - 从这些日志中自动提取摘要写入语义记忆库
- **注意点**
  - 对隐私内容做本地存储与加密（不上传外部服务）
  - 支持按主题/时间清除（忘记某段历史或某类数据）

实际实现中，可以在 SQLite 中维护类似下游表结构（示意）：

- `session_messages(session_id, ts_utc, role, content)`  
- `semantic_items(kind, content, tags, created_ts)`  

openPup 的 `memory` 模块已经对这些表做了封装。

#### 2.3 程序性记忆（Procedural Memory）

- **用途**
  - 表达「用户经常采用的操作流程」，例如：
    - 早盘前的例行检查
    - 写周报的惯用结构
    - 家居离家场景的标准动作顺序
  - 让助手不仅记得「事实」，还记得「习惯与流程」
- **实现建议**
  - 以 Playbook / 技能形式存在：
    - 每个 Playbook 对应一个或一组工具（或 Cron 任务）
    - 在文档中用结构化文本描述：
      - 前置条件
      - 步骤列表
      - 审批点（需要人工确认的环节）
  - 示例：`playbooks/work_morning_brief.md`, `playbooks/invest_daily_review.md`
- **注意点**
  - 所有程序性记忆都应当可以被用户随时查看与编辑
  - 高风险流程（如交易相关）必须明确写出风控条件与硬上限

---

### 3. 人 → 爪子 → 工具

- **核心是「人」**
  - openPup 的核心不是某个框架或某只「爪子」，而是一个有生命感、有记忆、会主动思考、在边界内自己做决定、会自我复盘和进化的「第二个你」。
  - 人格由 Persona + 三层记忆 + Playbook 共同决定。

- **人 → 爪子 → 工具**
  - **人**：Persona + 记忆 + 价值观 + Playbook，决定「为什么」「该不该」。
  - **爪子**：Loop 与调度逻辑（何时感知、何时行动），决定「什么时候」「以什么节奏」。
  - **工具**：执行某个具体动作（HTTP 请求、浏览器操作、家居控制等），只回答「怎么做」。

- **工程约束**
  - Loop/行为流程应当用 Playbook/配置表达（如 `playbooks/*.md` 或配置段），代码层只提供「时间轮 + 工具总线 + 审计」。
  - 不允许在 Loop 代码中硬编码具体业务策略（如某一只股票的买卖条件）；这些应属于 Persona/记忆/Playbook 范畴。

---

### 4. 记忆访问与安全策略

为了安全与可解释性，记忆访问也需要约束：

- **按需访问**
  - 工具或助手只在需要时查询记忆，而不是默认拉取所有内容
  - 检索请求需要包含明确的 Query 与用途说明
- **分层可见**
  - 不同权限等级的工具只允许访问对应层级的记忆（例如 L1 工具只能读部分长期记忆）
- **可审计**
  - 所有对长期记忆的写入与高风险读取都应当记录到 `runtime-audit.log`

---

### 5. 与 openPup runtime 的接口约定（实现提示）

- **Persona**：
  - 由 `persona` 模块从 `~/.openpup/workspace/persona/*.md` 组装为一段 Markdown。
  - runtime 在不同场景下注入不同片段（例如工作 / 投资 / 生活）。

- **Memory**：
  - 由 `memory` 模块提供 SQLite 底层与简单压缩操作：
    - `session_messages`：短期会话
    - `semantic_items`：长期语义记忆
  - Loop 与工具通过该模块读写记忆。

实现其他语言/外部 Agent OS 时，只要遵守：

- 不直接修改 Persona 文档本身，而是通过 openPup 的 workspace 约定读写；
- 对 Memory 的访问通过公开 schema（或工具协议）进行，就可以与本设计保持兼容。

  - 对每个会话维护：
    - 最近 N 条消息
    - 一个「小结」字段，定期更新以防上下文爆炸
- **注意点**
  - 不在会话记忆中存储敏感凭证（账号/密码/验证码）
  - 对含隐私的内容进行最小必要记录（记录意图而非原文）

#### 2.2 长期语义记忆（Semantic Memory）

- **用途**
  - 记住用户的长期偏好、反复出现的模式与关键知识点
  - 用于跨任务的「了解你是谁」与「你是怎么决策的」
- **实现建议**
  - 使用本地 SQLite + FTS + 向量检索（openPup 默认支持的记忆后端之一）
  - 建议拆分几个逻辑表/索引：
    - `preferences`：长期偏好（公司/行业/策略/工具等）
    - `projects`：重大项目的简要描述与状态
    - `invest_insights`：对市场、策略、个股的长期观点
  - 建立定期写入机制：
    - 每日/每周生成 `WORK_LOG.md` 和 `INVEST_LOG.md`
    - 从这些日志中自动提取摘要写入语义记忆库
- **注意点**
  - 对隐私内容做本地存储与加密（不上传外部服务）
  - 支持按主题/时间清除（忘记某段历史或某类数据）

#### 2.3 程序性记忆（Procedural Memory）

- **用途**
  - 表达「用户经常采用的操作流程」，例如：
    - 早盘前的例行检查
    - 写周报的惯用结构
    - 家居离家场景的标准动作顺序
  - 让助手不仅记得「事实」，还记得「习惯与流程」
- **实现建议**
  - 以 Playbook/技能形式存在：
    - 每个 Playbook 对应一个或一组工具（或 Cron 任务）
    - 在文档中用结构化文本描述：
      - 前置条件
      - 步骤列表
      - 审批点（需要人工确认的环节）
  - 示例：`playbooks/work_morning_brief.md`, `playbooks/invest_daily_review.md`

- **注意点**
  - 所有程序性记忆都应当可以被用户随时查看与编辑
  - 高风险流程（如交易相关）必须明确写出风控条件与硬上限

### 3. openpup 的人格核心（人 → 爪子 → 工具）

- **核心是「人」**
  - openpup 的核心不是某个框架或某只「爪子」，而是一个有生命感、有记忆、会主动思考、在边界内自己做决定、会自我复盘和进化的「第二个你」。
  - 人格由 Persona + 三层记忆 + Playbook 共同决定，而不是由某个工程模块名称决定。
- **人 → 爪子 → 工具**
  - 人：Persona + 记忆 + 价值观 + Playbook，决定「为什么」「该不该」。
  - 爪子：Loop 与调度逻辑（何时感知、何时行动），决定「什么时候」「以什么节奏」。
  - 工具：最终执行某个具体动作（HTTP 请求、浏览器操作、家居控制等），只回答「怎么做」。
- **工程约束**
  - Loop/行为流程应当用 Playbook/配置表达（如 `playbooks/*.md` 或配置段），代码层只提供「时间轮 + 工具总线 + 审计」。
  - 不允许在 Loop 代码中硬编码具体业务策略（如某一只股票的买卖条件）；这些应属于 Persona/记忆/Playbook 范畴。

---

### 4. 记忆访问策略

为了安全与可解释性，记忆访问也需要约束：

- **按需访问**
  - 工具或助手只在需要时查询记忆，而不是默认拉取所有内容
  - 检索请求需要包含明确的 Query 与用途说明

- **可解释回溯**
  - 当助手基于记忆做出重要决策时，应在输出中引用：
    - 使用了哪些记忆片段（摘要即可）
    - 这些记忆如何影响当前决策

- **隐私与删除权**
  - 设计命令/接口允许用户：
    - 删除指定范围的记忆（按时间/项目/主题）
    - 禁止在某些会话中写入长期记忆（临时「隐私模式」）

---

### 5. 与 Persona 的交互

- Persona 决定「如何解读记忆」与「如何使用记忆」：
  - 同一条记忆，在保守型 Persona 下可能导致更谨慎的决策，在激进型 Persona 下则可能推动动作
- 重要原则：
  - 记忆不应覆盖 Persona 中写死的红线
  - 当长期行为偏离 Persona 设定时，可以在日志或每周总结中提示用户进行调整（要么改 Persona，要么认定是一次性偏离）
